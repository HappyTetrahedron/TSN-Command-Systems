# Maps
Maps are the most visible part of the TSN Command Systems: the pre-defined and lovingly designed sector maps that crews can fly around in.

If you want to design your own maps, this document is the place to start.

## Overview of the Map System
First off: the map system has been overhauled in 2025, but the vast majority of maps were designed before then.
As a result, we have a load of "legacy maps" designed in the old system, which is much more effort to work with and more error-prone.
If you're intending to create a new map, you'll want to use the new map system.

Like all components of the Command System, the map source files are found in the folder `XML Files`.
There are three subfolders:
- `Maps` contains the source files for the maps.
- `Legacy Maps` contains the source files for legacy maps.
- `Generated Maps` contains the generated maps. These are created automatically and should not be edited.

The script `generate_maps.sh` in the root directory generates both the legacy maps and the new maps.
If you edit any maps, you must run this script afterwards.
The script requires python and automatically configures a virtual environment.

## Anatomy of a map file

A map file is an XML file containing data for the map system.
There are a number of requirements this file needs to adhere to.

- The map file is named `System.xml`, where "System" is the name of the star system this map represents - e.g. `Vrae.xml` for the Vrae system map.
- The map file is a valid Artemis mission XML (though it doesn't need to be able to run standalone, and in fact, it usually can't.)
- The XML contains the `start` section, and one `event` for each sector on the map.
- The `start` section must define some variables, which are treated as metadata by the map system (details below).
- Each event must be named `Sector N`, where N is the index of the sector, and must contain no conditions and all the necessary actions to create and configure the entities that should be in this sector.

### Metadata variables
Ordinarily, the `start` section of an Artemis mission file contains setup instructions that are executed once when the mission is loaded.
However, in a map file, the `start` section is abused for the purpose of storing map metadata.
The code in the `start` section is not transferred to the final mission XML generated by the Command Systems, and is never executed inside Artemis.

The start section generally looks as follows:
```
  <start id_arme="4076349e-e1c0-4950-8e05-27c894bfaff8">
    <set_variable name="Coordinate X" value="1454.0" />
    <set_variable name="Coordinate Y" value="210.0" />
    <set_variable name="Width" value="4.0" />
    <set_variable name="Height" value="3.0" />
    <set_variable name="Alignment" value="Hegemony" />
  </start>
```

It must define the following variables:
- `Width` indicates the width of the map, in number of sectors (1-5).
- `Height` indicates the height of the map, in number of sectors (1-5).
- `Alignment` indicates the alignment of the map. Valid values are `Hegemony`, `USFP`, `Neutral` and `Badlands`.
- `Coordinate X` and `Coordinate Y` indicate the pixel coordinates of this map on the map overview (the one seen on https://cic.tetrahedron.ch). If you don't know what values to put, you can leave them at 0 for the time being.

### Sector Events
The map must have one `event` node corresponding to each sector, which is named `Sector N` (N being the number of the sector).
For example, the event rendering the eighth sector is named `Sector 8`.

The sector event must not have any conditions.

Running the actions of a sector event should build the sector in question - so you will want to add any and all `create` actions needed to construct the sector, and you'll want to add actions to configure the object properties etc. of the created entities.

## Editing Maps

The recommended way to edit maps is to use the [Artemis Mission Editor](http://artemiswiki.pbworks.com/w/page/53389687/Mission%20Editor).
It contains a graphical interface to place objects within a sector.

Once you have finished your map, place it in `XML Files/Maps` and run the `generate_maps.sh` script.
Now, your map is available for inclusion when building the mission script.

To actually build the mission script, you can use the `XML Files/render.py` utility.
You will want to update its parameters (directly inside the file) to include your new map.

## Advanced Maps

Some maps contain additional logic to produce special effects, such as hazardous areas or moving entities.
Such logic cannot be added via the map's XML file, since the XML file is completely restructured by the map system.

The map system does, however, provide an alternative way to include additional XML scripts with a map.
Such additional scripts are placed in a separate file, and can utilize jinja to render their XML data.
The reason for this separation is to ensure that the map XML file with the sector entity data can always be edited in the Artemis Mission Editor, even if jinja is being used to generate advanced logic.

To create an advanced map like this, create an additional file called `System.jinja` to pair with your `System.xml` (remember, `System` is the name of your system).
Place the jinja file in the `Maps` folder, next to its partner XML file.

The jinja file will replace the default file used to render the XML data, so for the map to render properly, the jinja file must include the file `Maps/MapTemplate.jinja`:

```
{% include 'Maps/MapTemplate.jinja' %}

{# ... further code goes here ... #}
```

The jinja file can then define arbitrary additional Artemis `event` tags to handle the logic of the map.

It will be up to you that your event logic is sound and does not interfere with other maps.
In Artemis mission scripts, all variables are global and there is no concept of scope - so you'll just have to be careful.
There is no way for the map system to enforce isolation between maps.

### MapUtils
A jinja file with some useful macros for maps is provided.
It can be imported as follows:

```
{% import 'Maps/MapUtils.jinja' as maputil %}
```

The following useful macros are available:

#### `runIfInSector(mapName, []sectors)`
Call this macro to run an Artemis script snippet on the condition that the players are currently in a specific sector on your map.

You must provide the current map name, which you can pass along from the variable `g.map` that is available to you.

Example call:
```
{% call sysutil.runIfInSector(g.map, [1,5,9]) %}
  <if_variable name="Vrae_Pulsar_InRange" comparator="EQUALS" value="1.0" />
  <warning_popup_message message="Clear: Electromagnetic Radiation Nominal" consoles="MHWESCO">Electromagnetic Radiation Nominal</warning_popup_message>
  <set_variable name="Vrae_Pulsar_InRange" value="0.0" integer="yes" />
{% endcall %}
```

You may include further conditions in the event.

#### `runOnMapLoad(mapName)`
Call this macro to run an Artemis script snippet when the map is loaded.

You must provide the current map name, which you can pass along from the variable `g.map` that is available to you.

Note that this snippet may be run multiple times if the players jump out of your map and then back in.

Example call:
```
{% call sysutil.runOnMapLoad(g.map) %}
  <set_timer name="Vrae_Pulsar_Timer" seconds="1" />
  <set_variable name="Vrae_Pulsar_InRange" value="0.0" integer="yes" />
{% endcall %}
```

#### `runOnMapUnload(mapName)`
Call this macro to run an Artemis script snippet when the map is unloaded (i.e. when the players are leaving it).

You must provide the current map name, which you can pass along from the variable `g.map` that is available to you.

Note that this snippet may be run multiple times if the players jump out of your map, then back in, and then out again.

Example call:
```
{% call sysutil.runOnMapUnload(g.map) %}
  <set_variable name="Vrae_Pulsar_InRange" value="0.0" integer="yes" />
{% endcall %}
```
